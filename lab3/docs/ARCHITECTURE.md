# Архітектура проєкту

Загальний опис

У цій лабораторній роботі реалізував систему для збору, обробки та збереження даних від IoT-датчиків за допомогою serverless-сервісів AWS.

Для тестування використовую локальний емулятор, який генерує дані трьох типів датчиків: температури, вологості та освітленості.

Отримані вимірювання надсилаються до AWS через REST API. Далі вони проходять перевірку, потрапляють у чергу та обробляються окремою Lambda-функцією.

Хмарна архітектура

Основний шлях передавання даних:


IoT Emulator -> Amazon API Gateway -> AWS Lambda (Ingest) -> Amazon SQS -> AWS Lambda (Processor) -> Amazon RDS (MySQL)

Для отримання історії вимірювань використовується окремий маршрут:

Client -> Amazon API Gateway -> AWS Lambda (History) -> Amazon RDS (MySQL)


Основні компоненти

Емулятор датчиків:

Розташований у директорії `emulator/`. Генерує вимірювання трьох типів датчиків та надсилає їх через HTTP POST-запити. Для запуску також підготовлений Dockerfile.

Amazon API Gateway:

Приймає HTTP-запити від емулятора та передає їх до Lambda-функції. Для приймання вимірювань використовується маршрут `POST /measurements`.

Lambda Ingest:

Функція `lamp-store-lab3-iot-ingest` перевіряє ключ доступу та правильність отриманих даних. Після успішної перевірки додає повідомлення до Amazon SQS.

Amazon SQS:

Черга `lamp-store-lab3-iot-measurements` використовується для тимчасового зберігання вимірювань перед обробкою.

Lambda Processor:

Функція `lamp-store-lab3-iot-processor` отримує повідомлення з черги, визначає тип датчика, перевіряє значення та записує результат у MySQL.

Amazon RDS:

Для зберігання вимірювань використовую Amazon RDS з MySQL. Усі три типи датчиків зберігаються в таблиці `measurements`.

Lambda History:

Функція `lamp-store-lab3-iot-history` обробляє запити на отримання історії вимірювань. Вона виконує запит до MySQL та повертає результат у форматі JSON.

Безпека

Для перевірки запитів на приймання даних використовую ключ доступу, який передається через заголовок `x-api-key`.

Облікові дані для підключення до бази даних зберігаються в AWS Secrets Manager.

База даних RDS розміщена у приватній підмережі та не має публічного доступу. Lambda-функції, які працюють із базою, підключаються до неї через VPC.

Розгортання

Інфраструктура AWS створюється за допомогою Terraform.

Код Lambda-функцій розташований у директорії `functions/`, а конфігурація хмарних ресурсів — у `terraform/`.

Це дозволяє створювати та налаштовувати необхідні ресурси за допомогою конфігураційних файлів, а не вручну через AWS Console.

Результат

У результаті реалізовано систему, яка приймає вимірювання від трьох типів IoT-датчиків, передає їх через Amazon SQS, обробляє за допомогою AWS Lambda та зберігає в Amazon RDS.

Також реалізовано окремий REST API для отримання історії вимірювань конкретного датчика.
Бонусні компоненти

До основного конвеєра додані три компоненти.

Черга недоставлених повідомлень. Повідомлення, яке функція обробки не змогла опрацювати за три спроби, переміщується з основної черги в `lamp-store-lab3-measurements-dlq`. Деталі описані в `docs/DLQ.md`.

База DynamoDB. Функція обробки окрім MySQL записує кожне вимірювання в таблицю DynamoDB з ключем розділу `sensor_id` і ключем сортування `measured_at`. Функція історії може читати з будь-якого з двох джерел (параметр `source`). Деталі в `docs/NOSQL.md`.

Сховище S3 та датчик камери. Окрема Lambda-функція `upload-url` видає підписаний URL для завантаження. Зображення йдуть у S3 напряму, у чергу потрапляє лише посилання на об'єкт, а функція історії повертає підписані URL для читання. Деталі в `docs/BLOB.md`.

Функції обробки та історії працюють у приватній підмережі без NAT, тому для доступу до DynamoDB створений VPC endpoint типу Gateway. Функція `upload-url` працює поза VPC, бо їй не потрібна база даних.
