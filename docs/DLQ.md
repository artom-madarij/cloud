# Черга недоставлених повідомлень (DLQ)

Загальний принцип роботи

Іноді Lambda-функція не може обробити повідомлення з черги. Наприклад, у ньому може бути неприпустима одиниця виміру. Якщо таке повідомлення просто повертати в чергу, воно буде повторюватися знову і знову. Щоб цього не було, для основної черги налаштована черга недоставлених повідомлень (dead-letter queue, DLQ).

Налаштування

Для цього створена окрема черга Amazon SQS `lamp-store-lab3-measurements-dlq`. Повідомлення в ній зберігаються 14 днів.

До основної черги `lamp-store-lab3-iot-measurements` підключена політика redrive з параметром `maxReceiveCount = 3`. Це означає, що після трьох невдалих спроб обробки SQS сам переносить повідомлення в DLQ.

Для Lambda-функції обробки в event source mapping увімкнено режим `ReportBatchItemFailures`. Завдяки цьому функція повертає ідентифікатори лише тих повідомлень, які не вдалося обробити. Решта повідомлень із пакета вважається оброблена й видаляється з черги, тому одне погане повідомлення не зупиняє обробку інших.

Усе це описано в Terraform у файлі `terraform/dlq.tf`.

Перевірка роботи

Приймач перевіряє лише те, що поле `unit` є непорожнім рядком. А функція обробки знає, які одиниці допустимі для кожного типу датчика. Тому для перевірки надіслав вимірювання температури з одиницею `K`:

```bash
curl -s -X POST "$INGEST_URL" \
  -H "x-api-key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"sensor_id\":\"temperature-01\",\"sensor_type\":\"temperature\",\"value\":21.5,\"unit\":\"K\",\"location\":{\"lat\":49.84,\"lon\":24.03},\"measured_at\":\"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)\"}"
```

Приймач відповів `202 Accepted`, повідомлення потрапило в чергу. Функція обробки кожного разу завершувалась помилкою `Invalid measurement unit`, це видно в журналі CloudWatch:

```bash
aws logs tail /aws/lambda/lamp-store-lab3-iot-processor --since 15m --region eu-central-1 | grep "Failed to process"
```

Час видимості повідомлення в основній черзі становить 210 секунд, тому проходження трьох спроб займає близько 11 хвилин (3 × 210 секунд). Після цього повідомлення з'явилося в DLQ. Кількість повідомлень у ній перевіряється так:

```bash
aws sqs get-queue-attributes --queue-url "$DLQ" \
  --attribute-names ApproximateNumberOfMessages --region eu-central-1
```

Прочитати саме повідомлення можна командою `aws sqs receive-message` для URL черги недоставлених.

Під час цієї перевірки емулятор продовжував працювати, а нові вимірювання записувалися в базу. Отже, повідомлення з помилкою не заважає обробці всього потоку.

Хто і як розбирає чергу недоставлених

DLQ має розбирати той, хто відповідає за систему. Спочатку потрібно переглянути тіло повідомлення та запис про помилку в журналі. Далі є два варіанти. Якщо проблема в самих даних (як тут із одиницею `K`), повідомлення можна просто видалити. Якщо проблема була в помилці коду, після виправлення функції повідомлення можна повернути в основну чергу через redrive у консолі AWS або командою `aws sqs start-message-move-task`.

Важливо стежити за цією чергою, наприклад налаштувати сповіщення CloudWatch, коли в ній з'являються повідомлення. Інакше помилки залишаться непоміченими, а дані фактично будуть втрачені після завершення терміну зберігання.

Результати перевірки

- Повідомлення з некоректною одиницею вимірювання було прийняте з кодом `202`.
- Функція обробки тричі завершилась помилкою для цього повідомлення.
- Після трьох спроб повідомлення опинилося в черзі недоставлених.
- Обробка решти повідомлень не зупинялась.
