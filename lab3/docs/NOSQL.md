# Нереляційна база для сирих даних

Загальний принцип роботи

Окрім MySQL, кожне вимірювання зберігається в нереляційній базі Amazon DynamoDB. Для цього створена таблиця `lamp-store-lab3-measurements` з режимом оплати `PAY_PER_REQUEST`.

Ключ розділу таблиці — `sensor_id`, ключ сортування — `measured_at`. Час зберігається у форматі ISO 8601 UTC з однаковою кількістю знаків, тому порядок за рядком збігається з хронологічним порядком.

Окрім полів вимірювання, у запис додається ідентифікатор повідомлення SQS та вихідне повідомлення в первинному вигляді (поле `raw`).

Запис у таблицю виконує та сама Lambda-функція обробки, що й запис у MySQL. Якщо повідомлення доставляється повторно, запис із тим самим `sensor_id` і `measured_at` просто перезаписується, тому дублів не виникає.

Функція обробки працює в приватній підмережі без доступу до інтернету. Щоб вона могла звертатися до DynamoDB, у Terraform створений безкоштовний VPC endpoint типу Gateway.

Читання історії

Запит історії підтримує обидва джерела даних. Додатковий параметр `source` приймає значення `sql` (за замовчуванням) або `dynamodb`. Джерело, з якого взято відповідь, повертається в заголовку `X-Data-Source`.

Для перевірки використав такі запити:

```bash
curl -s "$H?from=$FROM&to=$TO&limit=5"
curl -s "$H?from=$FROM&to=$TO&limit=5&source=dynamodb"
```

В обох випадках API повертає масив вимірювань від найновішого до найстарішого.

Порівняння двох підходів

У MySQL запит історії виглядає як звичайний `SELECT` з умовою за датчиком і часом та сортуванням `ORDER BY measured_at DESC`. Швидкість забезпечує унікальний індекс за `sensor_id` і `measured_at`. У DynamoDB той самий запит виконується операцією `Query` з умовою `sensor_id = :s AND measured_at BETWEEN :from AND :to` і параметром `ScanIndexForward = false`.

Реляційна база зручна, коли потрібні складні запити: агрегації (середнє значення за добу), об'єднання таблиць, довільні фільтри за кількома полями. У DynamoDB такі запити неможливі або дорогі, бо без відповідного ключа доводиться перечитувати всю таблицю (операція Scan). З іншого боку, DynamoDB дуже швидко виконує саме той запит, під який спроєктований ключ: історія одного датчика за період.

Масштабування запису також відрізняється. Кожна Lambda-функція відкриває власне з'єднання з MySQL, тому при зростанні кількості датчиків кількість з'єднань може перевищити можливості бази. До DynamoDB звернення виконуються через HTTP API, пулу з'єднань немає, а дані розподіляються по партиціях за значенням `sensor_id`. Тому запис масштабується разом із кількістю датчиків без додаткового налаштування. Ще одна відмінність у вартості: RDS працює й коштує постійно, а DynamoDB оплачується за запити і має безкоштовний рівень.

Слабке місце DynamoDB — «гаряча» партиція, якщо один датчик пише дуже інтенсивно, і відсутність гнучких запитів.

Висновок

Для потоку телеметрії краще підходить DynamoDB: єдиний основний запит («дані датчика за період») повністю збігається з ключами таблиці, а запис легко масштабується. Реляційну базу варто залишити для аналітики та звітів, де потрібні агрегації. У цій роботі зберігаються обидва варіанти, і користувач може вибрати джерело параметром `source`.

Результати перевірки

- Вимірювання записуються в обидві бази.
- Запит історії з `source=dynamodb` повертає дані від нових до старих.
- Кількість записів у DynamoDB можна перевірити командою `aws dynamodb scan --select COUNT`.
