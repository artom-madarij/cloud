Збереження та читання історії вимірювань

Структура бази даних

Для збереження вимірювань використовую Amazon RDS MySQL 8.4.

Для всіх трьох типів датчиків створена одна таблиця `measurements`. У ній зберігаються дані про температуру, вологість та освітленість.

Вирішив використовувати одну таблицю, оскільки всі датчики передають дані однакового формату. Тип вимірювання визначається полем `sensor_type`.

У таблиці зберігаються такі поля:

- `measurement_id` — унікальний ідентифікатор вимірювання.
- `sensor_id` — ідентифікатор датчика.
- `measured_at` — час вимірювання.
- `sensor_type` — тип датчика.
- `value` — значення вимірювання.
- `unit` — одиниця виміру.
- `latitude` і `longitude` — координати датчика.
- `is_anomaly` — позначка про аномальне значення.
- `anomaly_reason` — причина аномалії.
- `processed_at` — час обробки даних.

Для таблиці використовується первинний ключ `measurement_id`.

Також створений унікальний індекс за двома полями: `sensor_id` і `measured_at`.

Цей індекс дозволяє швидше знаходити вимірювання конкретного датчика за часовим проміжком. Також він допомагає уникнути повторного запису одного й того самого вимірювання.

Отримання історії вимірювань

Для отримання історії створена окрема AWS Lambda-функція `lamp-store-iot-history`.

Вона підключається до MySQL і повертає вимірювання для вибраного датчика.

Для отримання історії використовується маршрут:

`GET /sensors/{sensor_id}/history`

Під час запиту можна передати три параметри:

- `from` — початок періоду.
- `to` — кінець періоду.
- `limit` — максимальна кількість записів.

Час передається у форматі ISO 8601 UTC.

Для перевірки використав такий запит:

```bash
HISTORY_URL="$(terraform output -raw iot_history_route | sed 's/{sensor_id}/temperature-01/')"

curl --get "$HISTORY_URL" \
  --data-urlencode "from=2026-11-16T00:00:00Z" \
  --data-urlencode "to=2026-11-17T00:00:00Z" \
  --data-urlencode "limit=10"
```

У відповідь API повертає масив JSON із вимірюваннями.

Приклад отриманих даних:

[
  {
    "measurement_id": "433",
    "sensor_id": "temperature-01",
    "sensor_type": "temperature",
    "value": 29.53,
    "unit": "°C",
    "location": {
      "lat": 49.8397,
      "lon": 24.0297
    },
    "measured_at": "2026-11-16T08:53:52.160Z",
    "is_anomaly": false,
    "anomaly_reason": null
  }
]

Результати повертаються від найновішого вимірювання до найстарішого.

Також перевірив неправильний параметр `limit=0`. У цьому випадку API повернув `400 Bad Request` з повідомленням про допустимий діапазон значень від 1 до 500.

Підключення Lambda до бази даних

History Lambda працює у приватній підмережі AWS VPC. База даних RDS також не має публічного доступу.

Для підключення використовуються змінні середовища:

- `DB_HOST` — адреса бази даних.
- `DB_PORT` — порт підключення.
- `DB_NAME` — назва бази даних.
- `DB_SECRET_ARN` — посилання на секрет з обліковими даними.

Ім'я користувача та пароль функція отримує з AWS Secrets Manager.

Для доступу до бази використовується бібліотека `mysql2/promise`.

Обмеження одночасних з'єднань

Під час використання Lambda важливо враховувати кількість одночасних з'єднань до бази даних.

На відміну від звичайного сервера, Lambda може запускати декілька екземплярів функції одночасно. Кожен такий екземпляр може створювати власне з'єднання з MySQL.

Через це при великій кількості запитів база може отримати більше підключень, ніж здатна обробити.

У моєму проєкті для підключення використовую пул з обмеженням одного з'єднання на екземпляр Lambda (`connectionLimit: 1`).

Для більших навантажень можна використовувати Amazon RDS Proxy, який допомагає керувати підключеннями до бази даних.

Результати перевірки

Для перевірки роботи виконав запити до API Gateway.

Отримав такі результати:

- Запит історії датчика `temperature-01` завершився з кодом `200 OK`.
- API повернув 10 вимірювань.
- Дані відсортовані за часом від нових до старих.
- Запит із `limit=0` повернув `400 Bad Request`.

Отже, вдалося реалізувати збереження вимірювань у MySQL та отримання їхньої історії через окрему AWS Lambda-функцію.
