# Обробка даних від IoT-датчиків

Загальний принцип роботи

Для обробки вимірювань використовую Amazon SQS та AWS Lambda.

Після надходження повідомлення до черги `lamp-store-lab3-iot-measurements` його отримує Lambda-функція `lamp-store-lab3-iot-processor`.

Функція перевіряє отримані дані, визначає тип датчика та виконує відповідну обробку. Після цього результат записується до таблиці `measurements` у базі даних MySQL.

Схема потоку даних

Емулятор (temperature, humidity, light)
                  |
                  | POST /measurements
                  v
             API Gateway
                  |
                  v
             Lambda Ingest
                  |
                  v
               Amazon SQS
                  |
                  v
            Lambda Processor -> DynamoDB (бонус)
                  |
                  v
                MySQL       

Якщо обробка завершується помилкою:
SQS -> повторна спроба -> після 3 невдалих спроб -> DLQ


Отримання історії:

Клієнт -> API Gateway -> Lambda History
                            |
                       MySQL / DynamoDB

Для всіх типів датчиків використовується одна Lambda-функція. Усередині неї є перевірка `sensor_type`, яка визначає, які правила потрібно застосувати до конкретного вимірювання. Три основні типи — temperature, humidity та light — мають власні правила діапазонів, а камера обробляється цією ж функцією за окремими правилами.

Обробка різних типів датчиків

В обов'язковій частині використовуються три основні типи датчиків:

- `temperature` — вимірювання температури.
- `humidity` — вимірювання вологості.
- `light` — вимірювання освітленості.

Для кожного типу встановлені свої допустимі межі та діапазон нормальних значень.

Для температури допустимий діапазон становить від -50 до 100 °C. Значення за межами 0–40 °C позначаються як аномальні.

Для вологості допустимий діапазон становить від 0 до 100%. Значення за межами 20–80% позначаються як аномальні.

Для освітленості допустимий діапазон становить від 0 до 100000 lux. Значення за межами 50–10000 lux позначаються як аномальні.

Якщо значення виходить за межі нормального діапазону, але залишається в допустимих межах, воно все одно записується до бази з позначкою `is_anomaly = true`.

Для таких вимірювань також зберігається причина аномалії у полі `anomaly_reason`.

Запис даних у MySQL

Після перевірки дані записуються до таблиці `measurements`.

Зберігаються ідентифікатор датчика, тип вимірювання, значення, одиниця виміру, координати та час отримання даних.

Також записується інформація про те, чи було виявлено аномалію.

Для підключення до MySQL Lambda використовує AWS Secrets Manager. Адреса бази даних та інші параметри підключення передаються через змінні середовища.

Захист від повторного запису

Під час роботи з чергами повідомлення іноді можуть надходити на обробку повторно. Наприклад, якщо виникла помилка або повідомлення було повторно доставлене сервісом SQS.

Щоб уникнути дублювання вимірювань, використовую унікальний індекс за полями `sensor_id` та `measured_at`.

Під час запису використовується команда `ON DUPLICATE KEY UPDATE`. Якщо вимірювання з таким датчиком і часом уже існує, новий рядок не створюється.

Це дозволяє уникнути повторного збереження одного вимірювання.

Обробка помилок

Якщо під час обробки повідомлення виникає помилка, Lambda повертає інформацію про невдало оброблений запис.

Для цього використовується механізм `ReportBatchItemFailures`.

Повідомлення, які були оброблені успішно, не потрібно надсилати повторно. Повідомлення з помилками можуть бути повторно доставлені SQS для наступної спроби обробки.

Також для Lambda налаштовано пакетну обробку повідомлень. За один виклик функція може отримувати до 5 повідомлень.

Повторна доставка повідомлень

Для основної черги налаштована черга недоставлених повідомлень (DLQ) `lamp-store-lab3-measurements-dlq`: після трьох невдалих спроб обробки (`maxReceiveCount = 3`) повідомлення переміщується в неї. Докладніше в `docs/DLQ.md`.

Якщо Lambda не змогла обробити повідомлення, воно не видаляється з основної черги SQS. Після завершення часу видимості повідомлення (visibility timeout), який становить 210 секунд, воно знову стає доступним для обробки.

Завдяки `ReportBatchItemFailures` успішно оброблені повідомлення з того самого пакета не потрібно надсилати повторно. Повторна доставка стосується лише повідомлень, для яких функція повернула помилку.

Результати перевірки

Під час тестування запустив емулятор, який надсилав вимірювання трьох типів датчиків до API Gateway.

Після цього повідомлення надходили до SQS та оброблялися Lambda-функцією.

Перевірив, що:

- Повідомлення успішно отримуються з черги.
- Lambda визначає тип датчика та застосовує відповідні правила.
- Оброблені вимірювання записуються до MySQL.
- Для аномальних значень зберігається відповідна позначка.
- Після обробки черга поступово очищується.

Під час тестування повідомлення успішно оброблялися, а кількість повідомлень у черзі зменшилася до нуля.

Доповнення: камера, DynamoDB та черга недоставлених

Для четвертого типу датчика, камери, функція обробки перевіряє одиницю виміру (`bytes`), допустимий діапазон розміру зображення від 0 до 1 МБ та правильність `object_key`. Зображення з нульовим розміром позначається як аномальне.

Окрім запису в MySQL, функція зберігає вимірювання в первинному вигляді в DynamoDB. Запис з однаковими `sensor_id` і `measured_at` просто перезаписується, тому ідемпотентність зберігається в обох базах.

Повідомлення, яке функція не змогла обробити, тепер не повторюється нескінченно. Після трьох невдалих спроб воно переміщується в чергу недоставлених, а решта пакета обробляється далі. Докладніше про це в `docs/DLQ.md`.
