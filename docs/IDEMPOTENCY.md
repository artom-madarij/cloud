Ідемпотентність оформлення замовлення

Ідемпотентність запиту дозволяє уникнути повторного створення замовлення, якщо клієнт повторно надсилає POST-запит через тайм-аут, втрату з'єднання або іншу помилку мережі.

Для цього використовується HTTP-заголовок `Idempotency-Key`. Кожен запит на оформлення замовлення повинен містити унікальний ключ.

Реалізація

Для збереження результатів використовується Redis із терміном зберігання 24 години (86400 секунд).

Алгоритм роботи:

1. Frontend генерує унікальний UUID та передає його в заголовку `Idempotency-Key`.
2. Backend перевіряє наявність ключа та коректність даних запиту.
3. Для перевірки однаковості запитів формується SHA-256 хеш нормалізованих даних замовлення.
4. Backend шукає результат у Redis за ключем `idempotency:{userId}:{idempotencyKey}`.
5. Якщо результат знайдено та хеш збігається, сервер повертає попередню HTTP-відповідь без повторного виконання операції.
6. Якщо ключ використаний з іншими даними, сервер повертає HTTP 409 Conflict.
7. Якщо результату в Redis немає, backend перевіряє його наявність у MySQL.
8. Якщо відповідний запис уже існує, сервер повертає збережений результат і відновлює його в Redis із залишком початкового терміну дії.
9. Якщо ключ раніше не використовувався, замовлення створюється в межах MySQL-транзакції, а результат зберігається в MySQL та Redis.

У Redis зберігаються:
- SHA-256 хеш запиту;
- HTTP-статус відповіді;
- тіло відповіді.

Redis використовується для швидкого отримання результату, а MySQL — як додаткове постійне сховище результатів та механізм захисту від повторного виконання операції. У таблиці `idempotency_keys` встановлено унікальний індекс за `user_id` та `idempotency_key`.

Обробка помилок

- Відсутній `Idempotency-Key` — HTTP 400 Bad Request.
- Повторне використання ключа з іншим набором даних — HTTP 409 Conflict.
- Повторний запит з тим самим ключем і тими самими даними — повернення збереженої відповіді без створення нового замовлення.

Результати тестування

Тестування виконувалося локально через Docker Compose із використанням Redis та MySQL.

1. Перше оформлення замовлення

Надіслано POST-запит до `/api/checkout` із заголовком `Idempotency-Key`.

Сервер успішно створив замовлення:
- HTTP-статус: 200 OK;
- orderId: 2;
- orderNumber: ORD-20261101-6845;
- totalAmount: 199.99;
- totalQuantity: 1.

Результат збережено в Redis та MySQL.

2. Повторний запит із тим самим ключем

Повторно надіслано той самий запит із тим самим ключем.

Сервер повернув попередню відповідь:
- HTTP-статус: 200 OK;
- orderId: 2;
- orderNumber: ORD-20261101-6845.

Нове замовлення не створювалося.

3. Перевірка повторного використання ключа з іншими даними

Надіслано запит із тим самим ключем, але зміненими даними замовлення.

Сервер повернув HTTP 409 Conflict, оскільки хеш нового запиту не збігся зі збереженим.

4. Перевірка відновлення результату з MySQL

Для перевірки резервного механізму відповідний ключ було видалено з Redis командою:

`DEL idempotency:1:c1e02edf-4565-47d9-ad5f-e42d1840716c`

Після цього повторно надіслано початковий запит із тим самим ключем та даними.

Сервер знайшов результат у MySQL і повернув:
- HTTP-статус: 200 OK;
- orderId: 2;
- orderNumber: ORD-20261101-6845.

Після цього результат було відновлено в Redis.

Перевірка TTL Redis показала 84204 секунди — залишок початкового 24-годинного терміну дії.

5. Перевірка кількості записів у базі даних

Після проведення всіх повторних запитів зафіксовано такі підсумкові показники:
- Загальна кількість створиних замовлень у таблиці `orders`: 2.
- Загальна кількість збережених ключів у таблиці `idempotency_keys`: 2.

Кількість замовлень залишилася незмінною після повторних дублюючих запитів.

Висновок

Реалізовано механізм ідемпотентності для endpoint `/api/checkout` із використанням Redis та MySQL.

Повторні запити з однаковим ключем і даними повертають раніше збережену відповідь без повторного створення замовлення. Використання того самого ключа з іншими даними відхиляється. Також перевірено відновлення результату з MySQL у разі відсутності відповідного запису в Redis.

Термін зберігання результату в Redis становить 24 години.
